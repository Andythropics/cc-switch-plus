# Associate External Skill Updates Explicitly

A locally imported Library Skill may acquire an Upstream Source through explicit user association. Its stable ID, immutable directory, content baseline, and deployments survive association. Linking a source alone preserves Skill contents, including Local Modifications. This extends ADR-0002's initial local-import provenance rule without making the external directory another authoritative managed copy.

The external-update inspector combines the global skills CLI lock file with currently present Skill directories. Historical lock entries without installed content are ignored. A name match is a recommendation, not an established association. Review may preselect a unique directory match, or otherwise a sole name match, while keeping the choice editable. Equally ranked ambiguous matches remain unselected. First association requires the user to explicitly invoke Link only or Link and update. Once associated, repository and repository-relative Skill path identify the upstream; content hashes detect changes. A marketplace slug is not a repository path, and a lock-file hash is not interchangeable with the Library's content hash.

Applying an external update revalidates the inspected state, stages and validates the external content, and uses the Library update engine's backup and atomic replacement. Local Modifications require explicit overwrite consent. Link and update explicitly includes replacing the external directory with a Library symlink through the existing import-and-replace protections, including first association without a recorded deployment and updates with unchanged content. The external directory is backed up before replacement. External and immutable Library directory names must match; a mismatch is rejected before mutation. An already-correct Library symlink remains intact. Link only never converts the external directory. If deployment restoration fails after the Library update, report recovery required and retain the backup; the result must not claim that deployment restoration succeeded.

Inspection itself never associates, imports, or overwrites content. The displayed scan is refreshed only when the user opens Sync CLI installations or explicitly rescans. Returning from Review reuses that scan and removes successfully processed candidates; failures remain available. Mutation-time revalidation still checks the approved state. For candidate-and-target observations, validation reads only the selected external directory and Library contents, plus relevant source and deployment metadata; it does not rebuild the full candidate matrix or hash unrelated Skills. Global import-and-replace checks use the same selected-directory scope while preserving the locked revalidation, backup, and rollback protections. Legacy whole-scan observations retain their original validation scope. Candidate-and-target observations allow unrelated candidates from the same scan to be processed sequentially without invalidating each other. Library entry, focus, timers, query invalidation, and manual source association never trigger that scan. Filesystem-heavy external commands run on blocking workers to keep the native UI responsive. Manual source association belongs to each Skill card; its existing Check Updates action remains the upstream update entry point. Review holds its original observation until the user applies or refreshes, so newer filesystem state cannot silently change an approved operation. After a completed mutation, dependent views refresh in the background without delaying return to the retained CLI list.

An external tool may write through a deployment link directly into the Library. Reconciliation can validate and record that state, but a backup created afterward contains the already-modified content. Recovering the version preceding the external tool's write requires an earlier backup.
